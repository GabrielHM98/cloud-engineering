# web-service 0.1.0

A reusable Helm application chart for **one stateless HTTP service per instance**.
Use it for an API, gateway or web frontend. Configure each service through values;
application source and Dockerfiles stay in `apps/`.

## Commit layout

Extract the ZIP from the root of `~/repos/app-releases`. It adds only
`charts/web-service/`, beside your existing `apps/` directory. It does not
replace application files or add a GitHub Actions workflow.

```bash
cd ~/repos/app-releases
unzip /path/to/web-service-chart.zip -d .
git add charts/web-service
git diff --cached --stat
git commit -m "Add reusable stateless HTTP service Helm chart"
```

Keep chart source here. Keep environment-specific values, real image digests,
Argo CD Applications and infrastructure installation configuration in
`paas-releases`. The publication workflow is a later step: this ZIP does not
publish a chart, change images, or deploy to a cluster.

## Render a generic app

Prerequisite: Helm 3. Tested with Helm 3.19.0. The chart declares Kubernetes
>=1.27; automated resource validation used Kubernetes 1.31 schemas. Other
versions and OpenShift admission must be checked against your actual cluster.

```bash
helm lint charts/web-service -f charts/web-service/examples/generic-app.yaml
helm template demo charts/web-service \
  --namespace demo \
  -f charts/web-service/examples/generic-app.yaml > /tmp/demo-api.yaml
```

`examples/rendered/generic-app.yaml` is that rendered output. The example image
`ghcr.io/example/demo-api:1.0.0` is illustrative; no such image is supplied.
The output contains a Deployment, ClusterIP Service, ServiceAccount and ConfigMap.

There is deliberately no implicit image or `latest` fallback. Set
`image.repository` and either `image.tag` or `image.digest`. A digest takes
precedence when both are present. Prefer a digest in deployment configuration.

For a real app, create environment values in `paas-releases`, configure the
real image, and render/validate before applying. A direct Helm installation,
if desired, uses an **existing** namespace:

```bash
helm upgrade --install demo charts/web-service \
  --namespace demo -f /path/to/your/real-values.yaml \
  --wait --timeout 5m
```

Namespaces, credentials and platform controllers are managed separately.

## Values contract

| Values | Purpose |
|---|---|
| `nameOverride`, `fullnameOverride` | Generated resource names; avoid changing names/selectors after installation |
| `image.*`, `imagePullSecrets` | Tag/digest and existing registry Secrets |
| `containerPort`, `service.port` | Nonprivileged application port and ClusterIP Service port |
| `command`, `args` | Optional image command and arguments |
| `env`, `envFrom` | Native Kubernetes environment variables and existing Secret/ConfigMap references |
| `configMap.enabled`, `configMap.data` | Nonsecret strings injected with envFrom; checksum triggers pod rollout |
| `serviceAccount.*` | Create a dedicated account, or name an existing one; token automount is disabled |
| `probes.*` | HTTP startup/readiness/liveness paths and timing; individually disableable |
| `resources` | CPU/memory requests and limits; tune from measurements |
| `strategy` | RollingUpdate (default) or Recreate |
| `podSecurityContext`, `securityContext` | Native pod/container settings |
| `tmp`, `extraVolumes`, `extraVolumeMounts` | Writable /tmp and additional native volume declarations |
| `nodeSelector`, `affinity`, `tolerations`, `topologySpreadConstraints` | Native scheduling configuration |
| `autoscaling.*` | Optional CPU HPA using autoscaling/v2 |
| `podDisruptionBudget.*` | Optional minAvailable budget for voluntary disruptions |
| `exposure.*` | Exactly one of none, Ingress or OpenShift Route |
| `networkPolicy.*` | Optional ingress-only isolation and explicit peer allowlist |

See the commented `values.yaml` for every default. JSON Schema rejects unknown
chart keys, wrong types, invalid ports and malformed digests. Native Kubernetes
objects (for example `env` and `affinity`) still require API schema/admission
validation. Global Helm values are allowed for parent-chart compatibility.

Helm merges maps but **replaces lists**: supplying `env` or `envFrom` replaces
that entire list. Map keys can be removed with null where Helm permits it.
The `checksum/config` pod annotation is reserved by this chart.

Configuration generated by the chart triggers rollout automatically. Changes
to externally managed Secrets and ConfigMaps do not: use your platform's
reloader or initiate a rollout after rotating them.

## Kubernetes and OpenShift behavior

Defaults: runAsNonRoot, RuntimeDefault seccomp, no privilege escalation,
ALL capabilities dropped, read-only root filesystem, bounded writable /tmp.
No fixed UID/fsGroup, SCC, cluster role or namespace is created. On vanilla
Kubernetes use an image with a numeric nonzero USER or supply an appropriate
`podSecurityContext.runAsUser`. On OpenShift the image must work with the UID
assigned by your SCC, with readable application files and writable mounted
paths. These defaults do not establish actual cluster admission compatibility.

Application images must listen on 0.0.0.0, use a port >=1024 and implement the
configured HTTP health paths. `/healthz` should check the running process;
`/readyz` should check whether it can accept requests. The default startup
window is approximately five minutes, during which liveness/readiness wait.
Tune it for model loading and resource availability.

Ingress requires an installed controller. Set its class and, for TLS, an
existing certificate Secret. Routes require the OpenShift Route API. Routes
use edge TLS termination and default HTTP-to-HTTPS redirect, relying on the
router's certificate; the backend hop is HTTP. The hostname must be covered
by the router certificate and DNS. Custom certificate provisioning and
reencrypt/passthrough Routes are outside this first version.

```bash
helm template demo charts/web-service \
  -f charts/web-service/examples/chemical-functions-web.yaml \
  -f charts/web-service/examples/openshift-route.yaml \
  --api-versions route.openshift.io/v1
```

For Argo CD, keep the Application name and Helm release name aligned when
using default `app.kubernetes.io/instance` resource tracking. If you need a
different naming policy, configure Argo tracking deliberately before rollout.

## Networking, scaling and availability

NetworkPolicy is off by default. Enabling it with no peers denies inbound
traffic. A configured peer is allowed only to the application's container
port. Egress is unrestricted. Other policies are additive; this is not a
complete namespace security policy. Enforcement needs a capable CNI. The
OpenShift example allows the `openshift-ingress` namespace; verify that this
matches your router/network implementation. If isolating catalog/predictor,
allow the web pods explicitly or the gateway will lose access.

HPA needs a metrics API (commonly metrics-server) and a CPU request. When
HPA is enabled the chart omits Deployment replicas so it does not reset the
HPA's desired count on every sync. Initial scaling remains asynchronous.
`examples/production.yaml` enables a 2-to-5 replica HPA and minAvailable=1 PDB;
it is an illustration, not a capacity assessment. A PDB with minAvailable=1
and only one replica can block voluntary eviction. PDBs do not guarantee
availability or prevent node failures.

## Chemical-functions examples

Three example files configure this same chart for web, catalog and predictor.
All images/tags are placeholders. The model and SQLite catalog must already
be in the corresponding images, as in the application Dockerfiles. These
examples do not train, fetch or mount the model.

Each can be a separate Helm/Argo release in the same namespace. The example
`fullnameOverride` values give stable Service names matching the gateway URLs.
Only the web service needs an external Route/Ingress.

Alternatively, an umbrella chart can depend on three aliases of this chart:

```yaml
# charts/chemical-functions/Chart.yaml (example, not created by this package)
apiVersion: v2
name: chemical-functions
version: 0.1.0
dependencies:
  - name: web-service
    alias: web
    version: 0.1.0
    repository: file://../web-service
  - name: web-service
    alias: catalog
    version: 0.1.0
    repository: file://../web-service
  - name: web-service
    alias: predictor
    version: 0.1.0
    repository: file://../web-service
```

Nest each component's values under its alias (`web:`, `catalog:`,
`predictor:`) in the parent values. Run `helm dependency update` when
intentionally updating dependencies and commit Chart.lock; use
`helm dependency build` in CI. Alias selector isolation is tested.

## Test and package

Test dependencies are optional for chart consumers; Helm rendering needs no
Python. Run from the repository root:

```bash
python3 -m venv /tmp/chart-tests
source /tmp/chart-tests/bin/activate
python -m pip install -r charts/web-service/tests/requirements.txt
python charts/web-service/tests/test_chart.py
helm lint charts/web-service -f charts/web-service/examples/generic-app.yaml
helm package charts/web-service --destination /tmp/chart-packages
```

Set `HELM=/absolute/path/to/helm` if Helm is not on PATH. The 29 tests cover
rendering, invalid configuration, digest precedence, probes, rollouts, Secret
references, HPA, PDB, ingress policies, scheduling and umbrella aliases. Built-in
resources are validated against Kubernetes 1.31 schemas; Route rendering has
structural assertions, not full OpenShift API/admission validation. No image
execution or live deployment was performed.

Increase Chart.yaml `version` when changing chart behavior. Charts under
`charts/infra/<name>/` should be separate domain-specific charts or maintained
upstream dependencies, rather than turning this stateless chart into a
stateful database/operator installer. No project license has been selected;
add your chosen license before inviting reuse.
